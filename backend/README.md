# Backend прогноза пассажиропотока трамваев

FastAPI-сервис, который отдаёт и REST API, и сам дашборд (`GET /`) —
отдельного React/Node-фронтенда нет, всё в одном контейнере.

## Структура проекта

```
backend/
├── app/
│   ├── main.py              — точка входа, запуск сервера
│   ├── schemas.py           — форматы JSON-ответов (Pydantic)
│   ├── data_loader.py       — загрузка и фильтрация прогноза
│   ├── geo_loader.py        — загрузка геоданных остановок
│   ├── events_loader.py     — реестр календарных/событийных поправок,
│   │                           уже применённых в прогнозе
│   ├── static/
│   │   └── index.html       — дашборд (HTML + vanilla JS + Chart.js + Leaflet)
│   └── routers/
│       ├── forecast.py      — эндпоинты прогноза
│       ├── geo.py           — эндпоинты карты
│       ├── events.py        — эндпоинт "что уже учтено в прогнозе"
│       └── export.py        — эндпоинты выгрузки CSV/XLSX
├── data/
│   ├── submission.csv           — финальный прогноз (route;date;hour;prediction)
│   ├── route_stops_map.csv      — координаты остановок
│   └── calendar_and_events.json — календарные правила и транспортные события
└── requirements.txt
```

Данные — финальные, боевые (не тестовая заглушка): 14 640 строк прогноза
на 10 маршрутов (1, 5, 7, 11, 12, 17, 25, 26, 28, 50) на ноябрь–декабрь
2025 года. Карта остановок доступна для маршрутов 1, 5, 7, 11, 12 — для
остальных пяти в исходном датасете нет географии.

## Запуск через Docker (рекомендуемый способ)

Dockerfile и docker-compose.yml лежат в **корне репозитория**
(`tram-forecast/`), не в этой папке — команда запускается оттуда:

```
cd tram-forecast
docker compose up --build
```

Сервис откроется на **http://localhost:8000**. Подробности и список
эндпоинтов — в `docs/for_jury.md`.

## Локальный запуск без Docker (для разработки)

1. Создать и активировать виртуальное окружение:
   ```
   python -m venv venv
   venv\Scripts\activate        # Windows
   source venv/bin/activate     # macOS/Linux
   ```

2. Установить зависимости:
   ```
   pip install -r requirements.txt
   ```

3. Запустить сервер (из папки `backend/`):
   ```
   uvicorn app.main:app --reload --port 8000
   ```

4. Открыть в браузере:
   - Дашборд: `http://127.0.0.1:8000/`
   - Интерактивная документация API (Swagger): `http://127.0.0.1:8000/docs`
   - Альтернативная документация (ReDoc): `http://127.0.0.1:8000/redoc`

## Эндпоинты

| Метод | Путь | Описание |
|---|---|---|
| GET | `/` | Дашборд (HTML-страница) |
| GET | `/health` | Проверка, что сервис жив (для мониторинга/Docker) |
| GET | `/forecast` | Прогноз с фильтрами: `route`, `date_from`, `date_to`, `hour` |
| GET | `/forecast/routes` | Список маршрутов со сводкой (есть ли карта, суммарный прогноз) |
| GET | `/geo/routes-with-map` | Список маршрутов, для которых есть география |
| GET | `/geo/route/{route}` | Геометрия маршрута (остановки по порядку, оба направления) |
| GET | `/events/applied` | Какие календарные/событийные поправки уже учтены моделью для даты и маршрута |
| GET | `/export/csv` | Выгрузка прогноза в CSV (те же фильтры, что у `/forecast`) |
| GET | `/export/xlsx` | Выгрузка прогноза в XLSX |

### Примеры запросов

```
GET /forecast?route=7&date_from=2025-11-01&date_to=2025-11-01
```
Прогноз по маршруту 7 на 1 ноября, по часам (горизонт «день»).

```
GET /forecast?route=7&date_from=2025-11-01&date_to=2025-11-30
```
Прогноз по маршруту 7 за весь ноябрь (горизонт «месяц»).

```
GET /events/applied?route=7&date_from=2025-11-13&date_to=2025-11-13
```
Что модель уже учла для маршрута 7 на 13 ноября (например, запуск линии Т1).

```
GET /geo/route/7
```
Обе линии маршрута 7 (туда и обратно) с координатами остановок для карты.

## Производительность

Проведён локальный нагрузочный HTTP-тест backend.

**Оборудование:** MacBook Air M2, 8 ядер / 8 ГБ RAM.
**Стек:** Python 3.13.5, FastAPI + Uvicorn, один worker (без масштабирования).

**Результаты:**

| Сценарий | RPS | p50 | p95 | p99 |
|---|---|---|---|---|
| Смешанная нагрузка, 50 параллельных запросов | 646 | 78,6 мс | 97,3 мс | 109,3 мс |
| Полная выдача всех 14 640 строк прогноза | 64,8 | — | 93,1 мс | — |
| Экспорт CSV | — | — | 63,2 мс | — |
| Экспорт XLSX | — | — | 119,6 мс | — |

Всего выполнено 9 650 запросов, ошибок — 0. Пиковое потребление памяти —
172,3 МБ.

Требование хакатона — «сотни RPS при p95 < 200–300 мс» на 2–4 vCPU / 2–4 ГБ
RAM. Результат укладывается в требование с запасом даже на одном worker'е
без включения дополнительных процессов/реплик.

## Дополнительные возможности сверх обязательного минимума

- Интерактивный веб-дашборд (единая страница, без отдельного фронтенд-сервиса).
- Фильтрация по маршруту, дате, периоду и часу.
- Три горизонта агрегации: день (по часам), месяц, весь прогнозный период.
- Графики (Chart.js), таблица и сводные карточки-агрегаты.
- Демонстрационный сценарий «а что если» — можно проверить гипотетическое
  мероприятие или ограничение движения и посмотреть, как оно могло бы
  повлиять на прогноз, без риска спутать это с фактическим прогнозом модели.
- Прозрачный блок «что уже учтено в этом прогнозе» — по выбранным маршруту
  и дате показывает реальные календарные/событийные поправки, уже
  применённые моделью, со ссылками на первоисточники.
- Карта остановок с разделением по направлениям движения (туда/обратно).
- Экспорт данных в CSV и XLSX.
- Автоматическая интерактивная документация API (Swagger UI на `/docs`,
  ReDoc на `/redoc`).
- Health-check эндпоинт для мониторинга и Docker.
- CORS для доступа с любого источника.
- Автоматическая валидация входных параметров запроса и понятные тексты
  ошибок (например, 404 с пояснением, если у маршрута нет географии).

## Область применимости и ограничения

Подробно — на самой странице дашборда, в блоке «Область применимости
модели», и в `docs/external_sources.md` (внешние источники) и
`docs/model_scope.md` (границы применимости модели). Коротко:

- Данные хранятся в памяти процесса, без БД — оправдано объёмом (14 640 строк).
- Карта доступна только для маршрутов 1, 5, 7, 11, 12.
- Горизонты «месяц» и «год» реализуются через `date_from`/`date_to` —
  это одна и та же фильтрация с разным диапазоном дат, без отдельных
  специальных эндпоинтов под каждый горизонт.
- Погода тестировалась ML-инженерами отдельно, но не дала прироста
  качества прогноза и не вошла в финальную модель.
- Аутентификации нет — не требовалась по условиям задания.
