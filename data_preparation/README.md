# Первичная обработка и аудит данных

`prepare.py` переносит в репозиторий использованный командой скрипт аудита labels и географии. Он проверяет исходные агрегаты, явно отмечает пропуски и готовит файлы для исследования. Исходные данные не изменяются.

## Входы и запуск

Распакуйте [архив задания](https://disk.yandex.ru/d/DiFwlfMOauxjBg). Нужны:

```text
dataset/
├── labels/
│   ├── labels_day_train.csv
│   └── labels_day_test.csv
└── spravochniki/
    └── …10…маршрутов.xlsx
```

В справочнике используются листы `Остановки GTFS_STOPS`, `Порядок_с_координатами` и `Маршруты GTFS_ROUTES`. Скрипт ожидает исходную структуру поставленного организаторами файла.

Из корня репозитория:

```bash
pip install -r data_preparation/requirements.txt
python data_preparation/prepare.py --dataset /path/to/dataset
```

Windows: `python data_preparation/prepare.py --dataset "C:\path\to\dataset"`.
Другой каталог результатов задаётся через `--output /path/to/output`.
Запускайте обычным Python, без `-O`: исходные проверки используют `assert`.

## Что делает скрипт

1. Проверяет точную схему `route;date;hour;boardings`, отсутствие пустых значений и повторных ключей, целочисленность, допустимые маршруты, часы 0–23 и неотрицательность target.
2. Проверяет временные границы: train — январь–август 2025, valid — сентябрь–октябрь. `labels_day_test.csv` содержит доступную историю для валидации, не target ноября–декабря.
3. Восстанавливает полную сетку десяти маршрутов и 24 часов каждого дня. Сохраняет `observed_row`, исходный `boardings_raw`, тип пропуска, `known_anomaly`, `target_available` и выбранную политику.
4. Сравнивает чувствительность простого диагностического профиля к обработке пропусков. Это не оценка финального ансамбля v3.
5. Готовит географию с проверкой координат и удалённых остановок. Сортирует остановки отдельно по маршруту, рейсу, направлению и порядку; не соединяет разные направления.

### Политики пропусков

| Политика | Поведение |
|---|---|
| `preserve` | Отсутствующие наблюдения остаются NaN |
| `zero` | Отсутствующие строки получают нулевой target |
| `exclude_anomaly` | Как `zero`, но все часы маршрута 50 за 21.09.2025 исключены из доступного target |

Ночной пропуск — кандидат на нулевое движение, а не доказанный ноль. Отсутствие валидаций не доказывает отсутствие пассажиров. Маршрут 5 сохраняется в сетке, несмотря на отсутствие собственной истории. Аномальный день маршрута 50 помечается для анализа, а не исправляется автоматически.

## Выходные файлы

По умолчанию результаты записываются в `data_preparation/output/` и исключены из Git:

- `train_*.csv`, `valid_*.csv` — сетки для трёх политик;
- `quality_summary.csv` — размеры исходных данных и сетки, пропуски, суммы;
- `sensitivity.csv` — диагностическое сравнение политик;
- `missing_by_route_hour.csv`, `missing_days.csv` — распределение пропусков;
- `route_stops_audit.csv`, `route_stops_map.csv` — аудит и пригодные для карты остановки;
- `map_coverage.csv`, `routes.csv` — покрытие карты и справочник маршрутов.

Контрольные результаты на предоставленном датасете:

| Период | Исходных строк | Строк сетки | Пропущено | Сумма исходного target |
|---|---:|---:|---:|---:|
| Январь–август | 46 234 | 58 320 | 12 086 | 46 912 710 |
| Сентябрь–октябрь | 11 317 | 14 640 | 3 323 | 12 754 481 |

География доступна для маршрутов 1, 5, 7, 11 и 12. Прямые линии между остановками не являются точной трассой рельсов.

## Связь с финальным ML

Финальный [`ml/src/load_data.py`](../ml/src/load_data.py) самостоятельно читает исходные labels и заполняет пропуски нулями. Файлы этого аудита не подменяют его вход. Политика `exclude_anomaly` сохранена для диагностики и не применяется автоматически к выбранному submission.

Не используйте весь январь–октябрь как историю для ранних проверочных периодов. [`ml/src/validate.py`](../ml/src/validate.py) отсекает обучение перед началом каждого фолда. Реестр внешних событий ведётся отдельно в [`docs/external_sources_for_final_solution/`](../docs/external_sources_for_final_solution/README.md).

## Дополнительная сверка сырых транзакций

Функция `raw_check(dataset_path, split='valid', max_chunks=2)` читает `train.csv` или `test.csv` частями и сравнивает успешные валидации (`validation_result == 1`) с labels на выбранных контрольных датах. По умолчанию это только частичная проверка. Для полного прохода передайте `max_chunks=None`; он может занять много времени. Основная команда выше не запускает чтение многогигабайтных транзакций.
