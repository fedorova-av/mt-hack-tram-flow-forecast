# Ограничения и план развития

## Ограничения текущей версии

| Ограничение | Практическое следствие |
|---|---|
| Менее одного полного года истории | Поведение следующей зимы проверено хуже, чем летние и осенние режимы. Январские каникулы есть в истории, но независимого второго зимнего сезона нет. |
| Подбор профилей на доступных временных фолдах | Локальные улучшения могут не повториться на ноябре–декабре. Основной сохранённый submission получил **0.89577** на скрытом периоде; заявлять цель 0.95 как достигнутую нельзя. |
| Сетевые события после 31 октября | Маршрут 5, T1 и восстановление трасс задаются правилами, а не оцениваются по фактическим валидациям ноября–декабря. Часть подтверждающих публикаций появилась внутри горизонта прогноза: для строгого прогноза «на 31 октября» такие сведения нужно отделять от заранее известных. |
| Новый маршрут 5 и коэффициент T1 | Для маршрута 5 нет собственной обучающей истории; спрос перенесён с маршрута 25. Коэффициент влияния T1 на маршрут 7 (`0.90` в сохранённой версии) — сценарное предположение. |
| Только агрегаты по маршруту и часу | Прогноз не показывает заполнение вагона, посадки на остановке или время ожидания. Малое число валидаций во время бесплатного проезда не означает малое число пассажиров. |
| Жёстко заданная конкурсная сетка и календарь 2025 года | `predict.py` проверяет ровно 14 640 строк. Для нового горизонта нужно изменить контроль сетки, праздники и события, затем повторить проверку качества. |

Ретроспективные эксперименты с **фактической погодой оцениваемых дат** не являются честным прогнозом за 61 день. Они не вошли в финальный инференс. Полные результаты и принятые/отклонённые гипотезы остаются в [`experiments.csv`](../ml/reports/experiments.csv), а ограничения источников — в [реестре](external_sources_for_final_solution/README.md).

## План развития

| Приоритет | Шаг | Критерий готовности |
|---|---|---|
| 1 | Зафиксировать воспроизводимый срез данных и событий на дату прогноза. Разделить заранее известные события и сообщения, появившиеся позже. | Для каждого внешнего правила записана дата публикации; ретроспективная проверка использует только доступную на своём отсечении информацию. |
| 2 | Добавить скользящие проверки для новых сезонов и маршрутов, включая независимую зимнюю выборку. | У каждой новой версии есть результаты по сезонам, маршрутам и горизонту, а также сравнение с сохранённой базой на одних и тех же ключах. |
| 2 | Калибровать события и новые маршруты отдельно от сезонной модели; исследовать диапазон T1 и аналоги запуска маршрута 5. | Для каждого сценария показаны допущения, диапазон прогноза и проверка на доступных аналогах; в основном варианте остаются только подтверждённые поправки. |
| 3 | Добавить мониторинг качества и обновление прогнозов по мере появления новых labels; при необходимости — доступный на момент прогноза прогноз погоды. | Регулярно измеряются WAPE и смещение по маршрутам/часам; переобучение не использует будущие факты и воспроизводится из зафиксированной версии входов. |

Изменение кода и документации само по себе не повышает конкурсный score. Новую версию стоит отправлять только после заметного и устойчивого улучшения на временных проверках и проверки того, какие сведения были доступны на дату прогноза.

## Ограничения приложения и интеграции

| Ограничение | Следствие и действие |
|---|---|
| Основной сервис расположен в `backend/`, Docker собирается из корня | Локальный запуск и smoke-тест проверены; сборку Docker необходимо подтвердить в среде с Docker. |
| Сервис загружает CSV, географию и события один раз при старте | Замена файла на диске не обновляет ответы работающего процесса; нужен перезапуск. Для частых обновлений потребуется управляемая загрузка с проверкой версии. |
| CSV проверяется по схеме, типам, датам, уникальности ключей и допустимости значений | Перед публикацией дополнительно проверять уникальность ключей, полноту сетки, допустимые даты/часы, неотрицательность и совпадение с утверждённым ML-артефактом. |
| Даты и диапазоны API проверяются; CORS открыт для всех источников; аутентификации нет | Для публичного доступа нужны список разрешённых origin, TLS и правила доступа; текущая конфигурация рассчитана на демо. |
| Дашборд использует внешние Chart.js, Leaflet и картографические тайлы | В офлайн-среде график или карта могут быть недоступны; для автономной демонстрации зависимости нужно разместить локально. |
| Геоданные есть только для пяти маршрутов; линии соединяют остановки по прямой | Карта не покрывает всю модель и не отражает точную трассу; нельзя выводить из неё спрос на отдельной остановке. |
| Нагрузочные результаты получены на отдельной оптимизированной копии в `docs/performance/` | Оптимизация перенесена в основной backend. Измеренные p95/RPS нужно перепроверять в целевой среде. |

## Ближайшие шаги по продукту

1. Поддерживать согласованность основного backend и канонического прогнозного CSV с [`ml/outputs/submission.csv`](../ml/outputs/submission.csv). Закрепить запуск и проверку `/health`, `/forecast`, `/events/applied`, `/geo` и обоих экспортов.
2. Добавить валидацию входных файлов и параметров API, проверку версии данных и понятный отказ при неполной сетке. Отдельно проверить, что интерфейс не применяет ML-события повторно, а сценарий «что если» всегда явно помечен как гипотетический.
3. После интеграции повторить функциональные и нагрузочные проверки в среде развёртывания. Для публичного использования закрыть CORS, определить политику доступа и обеспечить работу необходимых ресурсов интерфейса.
4. По мере появления реальных валидаций вести мониторинг ошибки и смещения по маршрутам, часам и режимам, обновлять модель только с соблюдением временной границы и версионировать опубликованный CSV вместе с реестром событий.
